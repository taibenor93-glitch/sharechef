## 2026-08-03 — Hebrew language lock (third language failure — structural fix)
Symptom: Micheli stuck in one language across all of Tai's sessions (Hebrew this week; English-vs-French earlier with a neighbor), on web Safari and the App Store app; recipe dropdown changed nothing; End session / app close changed nothing. Blocked launch-clip filming.
Root cause: language lived only in prompt persuasion, and the prompt argued with itself. The memory summarizer was ordered to "always note which language the user cooks in," the welcome-back greeting opened in that remembered language, and the "stay in the conversation's language / unclear audio never switches" clause consistently beat the "follow the user's live language" clause — so whatever language a session opened in became locked, in both directions. The Home dropdown never touched the voice session at all (typed recipes only, no Hebrew option). Third language-behavior failure (07-26, 07-29, 08-02) → per micheli-troubleshooter, prompt patches no longer acceptable.
Structural fix (deployed this date): deterministic session language in server.js — explicit user pick (sent in the auth frame) > profiles.language (new Supabase column, added 08-03) > device language from Accept-Language header > English; only the user's live speech outranks the pick. Memory is now ordered to never record language and to ignore any language already recorded (existing "cooks in Hebrew" notes self-clean on next merge). The dropdown is now a real voice-language control with Hebrew added, persisted on-device and on the account. Old App Store builds get the device-language default server-side with no update needed. Bonus fix: .topbar safe-area padding — top nav (Preferences/Sign out) was under the iOS status bar and untappable.
Verification rule: only Tai declares this fixed, after he picks English and hears English audio himself.

## 2026-07-29 — stuck in Italian across sessions / sessions kept resuming
Symptom: signed-in user (Tai's iPhone, v1.4 test build) greeted in Italian every session; clear attempts to switch language were ignored; ended sessions kept coming back.
Root cause: three mechanisms stacked — memory records the cooking language and the welcome-back greeting opens in it; the language rules said "stay in the conversation's language / unclear audio never switches" with nothing ranking the user's LIVE language above memory or resume; and the 3-hour resume window kept resurrecting saved cooks (the live App Store build can't send the deliberate "bye", so End session looks like a drop).

Recurrence note: second language-behavior failure in 4 days (see 07-26). If language behavior breaks a third time, stop patching prompts and build the structural fix: a scripted multi-language switch test against /api/test/chat run before every deploy.

## 2026-08-05 — WebSocket heartbeat + resume framing (~60s session drops)
Symptom: voice sessions on Railway were dropping roughly every 60 seconds, cutting Micheli off mid-cook with no warning.
Root cause: Railway idle-closes a quiet WebSocket after about 60s of no traffic (close code 1005), and neither the browser leg nor the OpenAI leg generated any traffic during silent moments (listening, thinking).
Fix (commit 9dca3a1, deployed via Railway): server.js now pings the browser leg every 25s, terminating after 2 missed pongs so the close handler runs cleanly (flushes cook state, closes the OpenAI leg); the OpenAI leg gets its own 25s keep-alive ping and is never terminated from that side by design. realtimeVoice.ts adds reconnect-after-drop: up to 3 attempts with backoff, a fresh auth token fetched on every reconnect, and Micheli briefed to resume the cook rather than restart. This same commit introduced the deliberate-End-session flag and frame, which turned out to carry its own race — see 2026-08-06 below.

## 2026-08-06 — "End session" resumed instead of ending (race in the 08-05 fix)
Symptom: tapping End session still occasionally greeted the next session with "welcome back, picking up where you were" instead of starting fresh.
Root cause: the 08-05 fix cleared cook state only inside the server's close handler, gated on a flag set by parsing the client's "bye" text frame; on a flaky mobile socket the close event could beat that frame's processing, so the flag never got set in time, the transcript got flushed and saved instead of cleared, and the next session loaded that stale cook_sessions row.
Fix (commit eb6cb8b, deployed via Railway): renamed the mechanism to intentionalEnd (client) / end_session (server frame type) and moved the cook-state clear to fire synchronously the instant the server receives the end_session frame, removing the race entirely; the client now also closes with an explicit code 1000. Verified via Railway /health returning {"status":"ok","model":"gpt-realtime","voice":"shimmer","apiKey":true} after deploy.
